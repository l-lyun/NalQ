# [Guide] OpenMD 문서 운영

이 문서는 OpenMD의 제품·UX·공유 계약·기술 문서를 언제 만들고 무엇을 원장으로 삼을지 정한다. 문서 수를 늘리는 것이 아니라 중요한 결정과 책임을 저장소에서 찾고 검토할 수 있게 하는 것이 목적이다.

## 기본 원칙

- 한 정보에는 원장 하나만 둔다. 다른 문서는 내용을 복제하지 않고 해당 절을 링크한다.
- 새 사용자 기능은 `docs/prd/`의 집중된 PRD 한 개로 시작한다.
- 화면 구조, 여러 화면의 분기, 공유 경계 또는 지속 기술 판단이 실제로 복잡할 때만 동반 문서를 추가한다.
- 확정, 제안, 열린 질문을 구분하고 열린 질문을 구현 가정으로 승격하지 않는다.
- 코드와 문서가 다르면 책임 원장을 먼저 확인한다. 현재 코드나 TRD가 제품 정책·UX·공유 계약을 자동으로 덮어쓰지 않는다.

## 문서 유형과 원장 책임

| 유형 | 현재 위치 | 원장 책임 | 만드는 시점 |
| --- | --- | --- | --- |
| Product Foundation | `docs/product.md` | 제품 목적, 원칙, 전역 내비게이션, 공통 용어 | 제품 전체의 판단 기준이 필요할 때 |
| PRD | `docs/prd/` | 사용자 문제, 목표, 제품 행동·정책, 범위, 관찰 가능한 수용 기준 | 새 사용자 가치나 제품 정책이 생길 때 |
| Flow | `docs/ux/flow-*.md` | 여러 화면의 순서, 분기, 중단, 재개, 복구 | PRD만으로 흐름을 이해하기 어려울 때 |
| Screen Spec | `docs/ux/screen-*.md` | 한 화면의 정보 구조, 행동 위계, 진입·이탈, 사용자 가시 상태 | 별도 UX 검토나 화면 상태 승인이 필요할 때 |
| Contract | `docs/contracts/` | 웹·앱·서버가 공유하는 입력, 출력, 오류, 권한, 멱등성, 데이터 의미 | 둘 이상의 애플리케이션이 같은 경계를 소비할 때 |
| Execution Plan | `docs/plans/` | 현재 작업의 기술 접근, 작업 순서, 진행 상태, 검증 | 여러 파일·단계에 걸친 복잡한 구현을 추적할 때 |
| TRD | `<application>/docs/technical/` | 애플리케이션 내부의 지속 구조, 상태 모델, 통합 결정, 기술 검증 | 비자명한 구현 판단이 이후 작업에도 남을 때 |
| ADR | `docs/adr/` | 중요한 선택의 맥락, 대안, 결정 이유, 영향, 대체 이력 | 결정 이유가 기능이나 실행 계획보다 오래 남을 때 |

`docs/plans/`와 `docs/adr/`는 첫 실제 문서가 필요할 때 만든다. 빈 계층을 미리 만들지 않는다.

## PRD, Execution Plan, TRD의 관계

```text
PRD: 사용자가 무엇을 왜 얻어야 하는가
  ↓
Execution Plan: 이번 변경을 어떤 순서로 구현하고 검증하는가
  ↓
TRD: 구현 뒤에도 남아야 할 앱 내부 구조와 판단은 무엇인가
```

간단한 변경은 Execution Plan이나 TRD 없이 PRD와 코드·테스트만으로 끝낼 수 있다. Execution Plan과 TRD는 PRD·UX·Contract의 미결정 사항을 확정하지 않는다.

## Contract 작성 원칙

- API Contract는 OpenMD가 소유하는 안정적인 요청·응답과 오류 의미를 정의한다.
- OpenAI, Notion과 같은 외부 제공자의 원시 요청·응답 형식을 클라이언트 계약으로 직접 노출하지 않는다. 제공자별 형식은 서버 어댑터 경계에서 OpenMD 도메인 형식으로 변환한다.
- 외부 제공자의 필드나 오류가 바뀌어도 웹·앱 계약이 함께 바뀌지 않도록 제공자 종속 정보와 공개 계약을 분리한다.
- 계약 예시에는 실제 토큰, 학습자료 원문, 사용자 답안이나 외부 제공자의 원시 payload를 넣지 않는다.
- Data Contract의 보존 기간, 삭제 연계와 추적 범위가 미결정이면 열린 질문으로 남기고 구현이나 운영 로그 정책에서 임의로 확정하지 않는다.

## 문서 생성 판단

1. 사용자 행동, 정책 또는 수용 기준이 바뀌면 PRD를 작성하거나 갱신한다.
2. 여러 화면의 분기·중단·복구가 핵심이면 Flow를 추가한다.
3. 한 화면의 구조와 사용자 가시 상태를 별도 승인해야 하면 Screen Spec을 추가한다.
4. 둘 이상의 애플리케이션이 같은 의미를 사용하면 Contract를 추가한다.
5. 복잡한 구현의 작업 순서와 진행 상태를 보존해야 하면 Execution Plan을 추가한다.
6. 구현 후에도 남을 비자명한 앱 내부 판단이면 TRD를 추가한다.
7. 검토한 선택지와 결정 이유가 장기간 필요하면 ADR을 추가한다.

오탈자, 작은 스타일 수정, 명백한 버그 복원, 국소 리팩터링, 일회성 회의 메모에는 새 제품 문서를 만들지 않는다.

## 문서 상태

| 한글 | 메타데이터 | 의미 |
| --- | --- | --- |
| 초안 | `draft` | 검토 전이며 바뀔 수 있음 |
| 검토 중 | `review` | 피드백을 반영하는 중 |
| 확정 | `approved` | 현재 설계·구현 기준으로 승인됨 |
| 구현 동기화 | `implemented` | 승인 상태와 별개로 구현과 맞춰졌음 |
| 폐기 | `deprecated` | 더 이상 사용하지 않으며 대체 원장을 링크함 |

초안 문서 안에도 확정 사항이 있을 수 있다. 문서 전체 상태와 개별 요구사항의 확정 여부를 구분한다.

## 문서가 없거나 충돌할 때

- 새 사용자 행동에는 최소 PRD 또는 이번 요청에서 동등하게 확인된 사용자 승인이 필요하다.
- 새 공유 경계는 Contract 없이 공개 계약으로 고정하지 않는다.
- TRD가 없어도 기존 관례로 충분한 단순 구현은 진행할 수 있다.
- 열린 질문에 따라 사용자 흐름이나 공유 의미가 달라지면 구현을 멈추고 결정을 요청한다.
- 충돌 시 제품 정책은 PRD, 화면 의미는 Screen Spec, 순서와 분기는 Flow, 공유 의미는 Contract, 앱 내부 구현은 TRD의 책임을 우선 확인한다.

## 링크와 중복 규칙

- 저장소 내부 문서는 상대 경로로 링크한다.
- 링크 문구에 대상의 책임이 드러나게 한다.
- 같은 정책, 상태표, 오류 목록을 여러 문서에 복사하지 않는다.
- 문서를 이동하거나 대체하면 모든 소비자 링크와 `docs/README.md`를 함께 갱신한다.
- `DESIGN.md`와 TRD는 현재 SEED 컴포넌트·props·토큰을 고정하거나 덮어쓰지 않는다.

## 작성·검토 체크리스트

- [ ] 이 문서의 책임과 비범위가 분명한가?
- [ ] 확정, 제안, 열린 질문이 구분됐는가?
- [ ] 다른 원장의 내용을 복제하지 않고 링크했는가?
- [ ] 수용 기준과 검증 방법이 관찰 가능하고 구현 방식에 과도하게 종속되지 않았는가?
- [ ] 상태와 관련 원장이 `docs/README.md`에 반영됐는가?
