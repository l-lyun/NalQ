# [PRD] 이메일 기반 자체 인증

- 관련 흐름: [인증 흐름](../ux/flow-authentication.md)
- 관련 계약: [인증 API](../contracts/contract-api-authentication.md), [사용자·인증 데이터](../contracts/contract-data-authentication.md)
- 관련 화면: [로그인 전 공개 랜딩](../ux/screen-public-landing.md), [첫 진입 온보딩과 NalQ 가이드](../ux/screen-onboarding.md)

## 사용자 문제

사용자는 자신의 학습자료와 풀이 기록을 안전하게 저장하고 여러 방문에 걸쳐 이어서 사용하려면 본인 소유임을 확인할 수 있는 개인 계정이 필요하다. 비밀번호를 잊은 경우에도 계정 존재 여부를 외부에 드러내지 않으면서 본인 이메일로 접근 자격을 다시 설정할 수 있어야 한다.

## 목표

사용자가 외부 소셜 계정 없이 이메일 소유를 확인하고 고유한 닉네임과 필수 동의를 설정해 가입한 뒤, 별도 로그인 없이 학습을 시작할 수 있게 한다. 비밀번호를 잊으면 가입과 분리된 이메일 확인을 거쳐 새 비밀번호로 변경하고 기존 세션을 모두 종료한 뒤 다시 로그인할 수 있게 한다.

## 확정된 요구사항

- 첫 배포의 회원가입 대상은 만 14세 이상으로 제한한다.
- 로그인 아이디는 이메일로 고정한다.
- 계정 활성화와 로그인 전에 이메일 소유를 확인한다.
- 이메일 인증은 사용자가 메일로 받은 6자리 코드를 직접 입력하는 방식이다.
- 인증 코드는 혼동 문자를 제외한 대문자 영문·숫자 alphabet `ABCDEFGHJKMNPQRSTUVWXYZ23456789`에서 `SecureRandom`으로 생성한다.
- 비밀번호는 8~64자이며 영문자와 숫자를 각각 하나 이상 포함하고 공백을 허용하지 않는다. 특수문자는 선택 사항이다.
- 이메일 가입은 2단계다. 1단계에서 이메일 인증과 비밀번호 설정을 마치고, 2단계에서 닉네임과 필수 약관 동의를 설정한다. 서비스 이용약관 동의 문구에서 만 14세 이상임을 함께 확인한다.
- 비밀번호는 확인 입력을 포함해 두 번 입력한다. 두 값의 일치는 클라이언트가 확인하며 서버에는 비밀번호 하나만 전송한다.
- 로그인 화면에서 `비밀번호를 잊으셨나요?`를 선택해 이메일 기반 비밀번호 재설정을 시작할 수 있다.
- 비밀번호 재설정은 가입 인증과 목적이 분리된 전용 이메일 인증 코드를 사용하고, 인증에 성공한 사용자는 가입과 같은 비밀번호 정책으로 새 비밀번호를 설정한다.
- `PASSWORD_RESET` 이메일 인증 코드는 발급 후 10분 동안 유효하고, 코드 입력 실패는 최대 5회까지 허용하며, 재발송은 마지막 발송 후 60초부터 요청할 수 있다.
- 비밀번호 재설정이 완료되면 해당 계정의 기존 로그인 세션을 모두 무효화하고 사용자는 새 비밀번호로 다시 로그인한다.
- 닉네임은 전역에서 고유하며 명시적인 중복 확인을 거쳐야 한다.
- 닉네임은 화면에 보이는 글자 기준 2~10자이고 공백 없이 한글·영문·숫자만 허용한다. 특수문자와 이모지는 허용하지 않으며 영문 대소문자는 구분하지 않고 중복을 판단한다.
- 필수 서비스 이용약관과 개인정보 수집·이용 동의를 모두 완료해야 가입할 수 있다.
- 필수 서비스 이용약관은 사용자가 작성했거나 저장·AI 처리에 필요한 권한이 있는 자료만 입력하고, 타인의 개인정보·기밀정보·무권한 저작물을 입력하지 않으며, AI 생성 결과를 원문과 함께 검토하고 합리적인 침해 대응에 협조할 의무를 포함한다. 이 의무는 NalQ의 최소 전송·보안·삭제·신고 대응과 생성 결과 검증 책임을 면제하거나 사용자에게 포괄적으로 전가하지 않는다.
- 초기 버전은 이메일·비밀번호 자체 인증만 제공한다. 소셜 로그인은 노출하거나 동작시키지 않는다.
- 사용자 소유 학습자료와 풀이 기록은 내부 사용자 ID에 귀속한다.

## 범위

- 이메일과 비밀번호를 이용한 가입 요청
- 이메일 인증 발송, 재발송, 확인
- 활성 계정의 로그인과 인증 상태 유지
- 현재 세션 로그아웃
- 이메일 기반 비밀번호 재설정과 완료 후 재로그인
- 인증이 필요한 화면과 데이터 보호
- 입력 오류, 인증 실패, 만료 상태의 복구 안내
- 닉네임 입력과 중복 확인
- 활성 사용자의 닉네임 변경
- 공개 베타 운영 약관 전문 열람과 필수 동의
- 가입 완료 직후 자동 로그인과 신규 사용자 최초 온보딩 판단

## 비범위

- 소셜 로그인과 소셜 계정 연결 UI/API의 실제 제공
- 소셜 신규가입의 서버 상태·재진입·`social_accounts` 상세 구현
- 사용자명 로그인, 전화번호 인증, 비밀번호 없는 로그인
- 조직 계정, 관리자 역할, 다중 프로필
- 이메일 변경, 계정 병합, 계정 탈퇴와 데이터 삭제
- 경험치, 랭킹, 친구, 꾸미기 프로필 속성의 선행 설계

## 핵심 규칙

### 확정

- 이메일은 모든 인증 흐름에서 동일한 정규화 규칙으로 비교하며, 같은 정규화 이메일로 계정을 중복 생성할 수 없다.
- 이메일 인증과 가입정보 제출이 끝나기 전에는 DB 사용자 행을 만들지 않으며, 보호된 데이터 접근이나 로그인 세션 발급도 허용하지 않는다.
- 인증 코드 입력은 양끝 공백 제거 후 대문자로 변환하고 정확히 6자리인지 확인한다. alphabet 밖의 문자와 `I`, `L`, `O`, `0`, `1`은 허용하지 않는다.
- 비밀번호 입력 정책은 사용자 요구에 따른 제품 정책이며, 정규식 제안은 `^(?=.*[A-Za-z])(?=.*\d)(?=\S{8,64}$).+$`이다.
- 세션 없음이 확인된 사용자의 기본 주소 `/`는 로그인 전 공개 랜딩을 보여준다.
- 로그인하지 않은 사용자가 보호 URL에 직접 접근하면 로그인으로 안내하고 안전한 원래 내부 URL을 보존한다. 로그인 성공 뒤에는 해당 목적지로 복귀하고, 원래 목적지가 없으면 홈으로 이동한다.
- 인증 bootstrap 중에는 공개 랜딩, 온보딩 또는 개인 화면을 먼저 노출하지 않는다. 네트워크·서버 오류로 세션 유무를 판정하지 못하면 비로그인으로 단정하지 않고 재시도를 제공한다.
- 로그인 등 공개 인증 응답은 계정 존재 여부를 불필요하게 드러내지 않는다.
- 명시적 로그아웃 후 클라이언트는 개인 학습정보와 인증 자격 증명을 제거하고 공개 랜딩으로 대체 이동하며, 뒤로 가기로 보호 화면을 다시 볼 수 없어야 한다.
- 비밀번호 재설정 이메일 제출 결과는 계정 존재 여부와 재설정 가능 여부를 구분하지 않는 동일한 접수 안내를 제공한다.
- 재설정 메일의 실제 발송 여부나 전달 실패는 공개 응답에서 구분하지 않고 운영 상태로만 확인한다. 재설정 요청 자체를 접수할 수 없는 공통 장애는 입력한 이메일의 계정 상태와 무관하게 같은 실패 안내를 제공한다.
- 비밀번호 재설정 코드는 가입 인증 코드와 목적·상태를 분리한다. 한 흐름에서 발급된 코드를 다른 흐름의 인증 근거로 사용할 수 없다.
- 가입과 비밀번호 재설정은 이메일 발송, 코드 생성·입력 검증과 요청 제한의 공통 동작을 가능한 범위에서 일관되게 사용한다. 이 공통화가 `SIGN_UP`과 `PASSWORD_RESET`의 목적, 진행 상태와 발급 코드를 합치거나 공유한다는 의미는 아니다.
- `PASSWORD_RESET` 코드는 발급 후 10분이 지나면 만료되고, 잘못된 코드를 5회 입력하면 남은 유효시간과 관계없이 즉시 무효화한다. 재발송은 마지막 발송 후 60초가 지나야 가능하며, 새 코드를 발급하면 이전 재설정 코드는 즉시 무효화한다.
- 재설정 코드 확인이 성공하기 전에는 새 비밀번호를 확정할 수 없고 로그인 세션도 발급하지 않는다.
- 새 비밀번호와 확인 입력은 가입과 같은 8~64자, 영문자·숫자 각각 하나 이상, 공백 불가 정책을 사용한다. 두 값의 일치는 클라이언트가 확인하며 서버는 새 비밀번호 하나를 다시 검증한다.
- 비밀번호 재설정에 성공하면 기존의 모든 로그인 세션을 즉시 무효화하고 자동 로그인하지 않는다. 사용자는 로그인 화면에서 새 비밀번호로 다시 로그인해야 한다.
- 재설정 최종 제출은 한 번만 비밀번호를 변경한다. 처리 중에는 중복 제출을 막고, 이미 완료된 재설정 자격으로 다시 제출해 비밀번호나 세션 상태를 반복 변경할 수 없다.
- 로그아웃 후 클라이언트는 개인 학습정보와 인증 자격 증명을 제거하고, 보호 화면으로 돌아갈 수 없어야 한다.
- 비밀번호 원문, 인증 코드 원문, 접근·Refresh Token 원문을 DB·Redis·로그·분석 사건에 남기지 않는다.
- Refresh Token은 DB에 저장하지 않고 Redis에서 회전과 재사용 탐지를 관리한다.
- Access Token의 유효시간은 발급 시점부터 5분이다.
- 향후 소셜 계정은 제공자와 제공자 내부 사용자 식별자의 조합으로 구분하며, 이메일 문자열이 같다는 이유만으로 자동 병합하지 않는다.
- 닉네임 중복 확인 성공은 해당 닉네임의 예약을 뜻하지 않는다. 사용자가 확인 후 닉네임을 바꾸면 확인 상태를 즉시 무효화하고, 최종 가입 제출 시 서버가 형식과 중복을 다시 검증한다.
- 닉네임은 NFC로 정규화한 표시 값 하나만 사용자 행에 저장하고, 영문 대소문자를 구분하지 않는 DB 비교와 `UNIQUE` 제약으로 최종 중복을 막는다.
- 필수 서비스 이용약관과 개인정보 수집·이용 동의의 버전과 동의 시각은 별도 이력 테이블 없이 사용자 행에 함께 저장한다.
- 첫 공개 베타 약관 전문과 개인정보처리방침은 프론트엔드의 공개 문서를 단일 원장으로 사용하며, 회원가입에서도 같은 버전과 전문을 보여준다.
- 마케팅 수신 동의는 실제 목적과 정책이 정해지기 전에는 노출하지 않는다.
- 향후 소셜 신규가입은 제공자 인증 후 이메일 가입의 2단계와 같은 닉네임·필수 동의 단계로 진입하고 비밀번호를 요구하지 않는다. 소셜 버튼은 MVP에 노출하지 않는다.

### 구현 확정

- 이메일 인증 단계에는 사용자 행을 만들지 않고 Redis에 정규화 이메일의 keyed digest를 기준으로 인증 코드 상태를 저장한다.
- 인증 코드 검증에 성공하면 UUID v4 형식의 일회성 `signUpToken`을 발급한다. 서버는 원문 대신 SHA-256 digest와 인증된 이메일 정보를 Redis에 15분간 저장하고, 클라이언트는 원문을 메모리에서만 보관한다.
- 2단계의 `signUpToken`, 비밀번호, 닉네임과 필수 동의를 최종 검증한 뒤 사용자 행을 처음 `ACTIVE`로 생성한다. 가입을 중단하거나 자격이 만료되면 DB에 미완료 사용자 행을 남기지 않는다.
- 가입 완료 시 세션을 발급하고 현재 사용자를 확인한 뒤 [첫 진입 온보딩과 NalQ 가이드](../ux/screen-onboarding.md)의 신규 사용자 자동 노출 판단을 거친다. 대상이면 가입·인증 이력으로 돌아가지 않는 대체 이동으로 `/onboarding`에 진입하고, 온보딩 이탈 뒤 홈으로 이동한다. 이메일 가입 사용자에게 별도 로그인을 요구하지 않는다.
- 인증 코드 TTL은 10분, 실패 허용은 5회, 재발송 간격은 60초다. 재발급하면 이전 코드를 즉시 무효화한다.
- Refresh Token은 사용할 때마다 회전하며, 사용한 토큰의 재사용이 감지되면 해당 세션 또는 token family를 폐기한다.
- Refresh Token은 클라이언트에는 opaque하게 취급하고, 서버 형식은 `<randomSessionId>.<256-bit random secret>`이다. session ID는 조회용일 뿐 인증 근거로 신뢰하지 않는다.
- 비밀번호 해시는 Argon2id를 사용한다.

## 수용 기준

- 유효한 이메일과 서로 일치하는 정책 충족 비밀번호를 입력하고 이메일 인증을 완료하면 공통 가입정보 단계로 이동한다.
- 이메일을 인증하기 전에는 올바른 비밀번호를 입력해도 보호된 사용자 데이터에 접근할 수 없다.
- 사용자는 메일로 받은 유효한 6자리 코드를 입력해 이메일 소유를 확인하되, 닉네임과 필수 동의를 마치기 전에는 활성 계정이 되지 않는다.
- 형식에 맞는 닉네임도 중복 확인을 통과해야 가입할 수 있으며, 확인 후 값을 바꾸면 다시 확인해야 한다.
- 중복 확인 직후 다른 사용자가 닉네임을 선점하면 최종 제출이 거절되고 이메일·닉네임 외 입력 가능한 상태와 약관 동의는 보존된다.
- 서비스 이용약관과 개인정보 수집·이용 동의를 모두 선택해야 가입을 완료할 수 있다.
- 가입 시 동의하는 서비스 이용약관에서 사용자 자료 의무, AI 결과 검토와 침해 대응 협조, NalQ가 유지하는 처리·보호·신고 대응 책임을 확인할 수 있으며, 운영자의 책임을 포괄적으로 배제하는 문구는 포함되지 않는다.
- 유효한 `signUpToken`으로 최종 가입의 DB 확정이 성공한 경우에만 `ACTIVE` 사용자와 두 필수 동의의 버전·동의 시각이 같은 사용자 행에 저장된다.
- 정상적으로 가입과 세션 발급이 모두 완료되면 별도 로그인 화면을 거치지 않고 신규 사용자 자동 온보딩 판단을 거쳐 대상이면 `/onboarding`에 도착한다.
- DB 가입 확정 뒤 세션 발급이 실패해 `AUTH_011`을 받으면 같은 가입 요청을 반복하지 않고 로그인 화면으로 이동한다.
- 최종 가입 결과가 불명확한 네트워크 오류나 안정적인 오류 코드가 없는 5xx를 받은 브라우저는 가입 완료를 반복해 새 세션을 발급받으려 하지 않고 refresh를 한 번 시도한다. 세션을 복구하지 못하면 로그인으로 이동한다.
- 잘못된 코드는 사용 횟수 정책에 따라 거절되고, 만료·시도 소진·재발급으로 무효화된 코드는 사용할 수 없다.
- 활성 사용자가 올바른 이메일과 비밀번호로 로그인하면 인증 상태가 만들어지고 현재 사용자 정보를 조회할 수 있다.
- 비인증 사용자의 기본 주소는 공개 랜딩을 보여주고, 보호 URL 직접 접근은 로그인 뒤 복귀할 안전한 내부 목적지를 보존한다.
- bootstrap 중에는 랜딩·온보딩·개인 화면이 먼저 노출되지 않으며 세션 판정 실패에는 다시 시도할 수 있다.
- 명시적 로그아웃은 서버 응답 성공 여부와 관계없이 현재 기기의 개인 상태를 제거하고 공개 랜딩으로 대체 이동한다.
- 잘못된 로그인 정보에는 어떤 필드가 틀렸는지 또는 계정 존재 여부를 구분하지 않는 오류를 받는다.
- 로그인 화면에서 `비밀번호를 잊으셨나요?`를 선택하면 이메일 입력부터 비밀번호 재설정을 시작할 수 있다.
- 가입된 이메일과 가입되지 않았거나 재설정할 수 없는 이메일에 대해 재설정 이메일 제출 직후의 상태·문구·응답 형태로 계정 존재 여부를 구분할 수 없다.
- 재설정 메일의 실제 발송·전달 성공 여부는 공개 응답에서 드러나지 않으며, 요청 자체의 공통 장애도 계정 상태에 따라 다른 안내를 만들지 않는다.
- 가입 인증용 코드로 비밀번호 재설정을 진행할 수 없고, 비밀번호 재설정용 코드로 가입 인증을 완료할 수 없다.
- `SIGN_UP`과 `PASSWORD_RESET`이 공통 이메일 인증 동작을 사용하더라도 목적별 진행 상태와 코드는 서로 분리되며, 한 목적의 코드 발급·검증·무효화가 다른 목적의 상태를 변경하지 않는다.
- 유효한 재설정 전용 코드를 확인한 사용자만 새 비밀번호와 확인 값을 입력할 수 있다.
- 새 비밀번호가 가입 비밀번호 정책을 충족하지 않거나 확인 값과 일치하지 않으면 비밀번호가 변경되지 않는다.
- 유효한 재설정 자격으로 새 비밀번호 변경이 성공하면 기존 모든 로그인 세션에서 보호된 데이터에 더 이상 접근할 수 없고, 자동 로그인 없이 로그인 화면으로 이동한다.
- 비밀번호 변경이 실패하면 기존 비밀번호와 세션 상태를 성공한 것으로 변경하지 않으며 사용자는 안전하게 다시 시도하거나 재설정을 다시 시작할 수 있다.
- 발급 후 10분이 지났거나 5회 입력에 실패한 `PASSWORD_RESET` 코드는 새 비밀번호 설정에 사용할 수 없고, 마지막 발송 후 60초가 지나면 새 코드 요청 행동을 확인할 수 있다.
- 재설정 요청 한도를 초과하면 계정 존재 여부를 드러내지 않는 안내와 다시 시도할 수 있는 시점을 확인할 수 있다.
- 비밀번호 변경 처리 중 같은 요청을 반복 제출할 수 없고, 이미 완료된 재설정 자격을 다시 제출해 비밀번호를 반복 변경하거나 로그인 세션을 만들 수 없다.
- 유효한 로그인 상태는 Redis 기반 Refresh Token 회전 정책 범위에서 앱 재실행 후에도 복구할 수 있다.
- 한 번 회전되거나 로그아웃으로 폐기된 Refresh Token으로 세션을 다시 만들 수 없다.
- 소셜 로그인 선택지는 초기 버전에 표시되지 않는다.

## 계측 제안

- 가입 요청, 인증 코드 발송·재발송, 인증 성공·만료·시도 소진, 로그인 성공·실패, 비밀번호 재설정 요청·코드 확인·완료·실패·제한, 갱신 성공·재사용 탐지, 로그아웃 사건을 민감 값 없이 기록한다.
- 가입 요청에서 이메일 인증 완료까지의 이탈 지점을 확인하되 이메일 주소, 토큰, 비밀번호는 분석 속성으로 보내지 않는다.
- 비밀번호 재설정 단계별 이탈과 실패를 확인하되 이메일 주소, 인증 코드, 새 비밀번호와 재설정 자격은 로그·분석 속성에 남기지 않는다.

## 열린 질문

- 비밀번호 재설정 메일 요청의 별도 과다 요청 기준과, 해당 기준을 초과했을 때 추가로 적용할 재시도 대기시간은 얼마로 할지
- 이메일 코드 확인 후 새 비밀번호를 제출할 수 있는 일회성 재설정 자격의 유효시간은 얼마로 할지
- 새 비밀번호가 기존 비밀번호와 달라야 하는지와 과거 비밀번호 재사용 제한을 둘지
- 정지·탈퇴 계정처럼 로그인할 수 없는 계정의 재설정 요청을 내부적으로 어떻게 처리할지. 공개 응답은 계정 상태를 구분하지 않는다.
- Refresh Token의 최종 수명과 웹/앱별 안전한 전달·보관 방식
- 여러 기기 동시 로그인 허용 수와 `모든 기기에서 로그아웃` 제공 여부
- 닉네임 금칙어·신고 정책
- 정지 계정의 안내·복구 방식
