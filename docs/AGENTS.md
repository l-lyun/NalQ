# Product Documentation Guide

`docs/`는 제품 설계의 원장이다. 구현 결과를 설명하기 위한 사후 문서가 아니라, 구현 전에 사람과 전문 에이전트가 같은 결정을 읽는 기준으로 사용한다.

## Working Rules

- 먼저 `docs/README.md`에서 요청과 직접 관련된 문서만 찾는다.
- 문서를 새로 만들거나 분리할 때는 `docs/documentation-guide.md`를 따른다. 요청마다 PRD·화면·Flow·TRD·Contract를 모두 만들지 않는다.
- 새 사용자 기능은 집중된 PRD 하나로 시작하고, 실제 복잡성이 있을 때만 필요한 동반 문서를 추가한다.
- `확정`, `제안`, `열린 질문`을 섞지 않는다. 합의되지 않은 내용을 확정 사실처럼 작성하지 않는다.
- 한 정보에는 하나의 원장을 둔다. 다른 문서에서는 복제하지 말고 상대 경로로 연결한다.
- 기능명세는 사용자 가치와 관찰 가능한 수용 기준을 다룬다. 코드 구조, 프레임워크 사용법, 세부 DB 스키마는 각 구현 영역의 문서로 보낸다.
- 화면 구조가 핵심이면 `docs/screens/`, 기능 규칙이면 `docs/features/`, 순서와 분기이면 `docs/flows/`, 팀 간 입력·출력 합의이면 `docs/contracts/`를 사용한다.
- 새 결정이 기존 결정과 충돌하면 기존 문서를 조용히 덮어쓰지 말고 변경 이유와 영향 범위를 기록한다.
- 문서가 구현보다 오래되었다고 추정하지 않는다. 불일치는 열린 문제로 보고한다.

## Human Checkpoints

이 저장소는 자동 에이전트 파이프라인을 사용하지 않는다.

- 기본 작업 단위는 전문 에이전트 한 명이 끝낼 수 있는 범위다.
- 두 전문 영역이 꼭 필요하면 사용자가 요청에서 명시하거나, 첫 에이전트가 필요한 다음 작업을 제안하고 종료한다.
- 기획 → 설계 → 퍼블리싱 → 기능 구현 사이에는 사용자의 검토가 있다.
- 다음 단계 산출물을 선행 작성하거나 다른 에이전트를 자동 호출하지 않는다.

## Document Status

문서 상단에 가능하면 다음 중 하나를 기록한다.

- `초안`: 검토 전이며 바뀔 수 있다.
- `검토 중`: 피드백을 받고 있다.
- `확정`: 현재 구현 기준이다.
- `폐기`: 더 이상 사용하지 않으며 대체 문서를 링크한다.

상태가 `확정`이어도 문서 안의 `열린 질문`은 확정 사항이 아니다.
