# [TRD · Server] 퀴즈 채점 서버 설계

- 상태: 초안 — 프론트 UX 선행, 서버 미구현
- 제품 정책: [퀴즈 생성·풀이·결과·복습 PRD](../../../docs/prd/prd-quiz-learning.md#채점-수정과-서술형-자기평가)
- 사용자 흐름: [퀴즈 생성부터 복습까지](../../../docs/ux/flow-quiz-solving.md#d-결과)
- 현재 공유 계약: [학습자료·퀴즈·복습 API 계약](../../../docs/contracts/contract-api-quiz-learning.md#본-퀴즈-제출과-자기평가)

## 1. 문서 책임

이 문서는 서버가 먼저 판정한 단답형 채점 결과를 사용자가 수정할 수 있게 하기 위한 서버 내부 상태, 계산 경계와 향후 검증 기준을 정의한다. 어떤 문제 유형을 사용자가 수정할 수 있는지는 기능명세가, 공개 요청·응답과 오류 의미는 API 계약이 원장이다.

이번 단계에서는 프론트 UX만 먼저 설계한다. 현재 API 계약에는 단답형 판정 수정 요청이 없으므로 서버 코드와 운영 프론트 연동은 변경하지 않는다.

## 2. 확정된 제품 경계

- 객관식은 서버 자동 판정만 사용하며 사용자 수정 대상이 아니다.
- 답을 작성한 단답형은 서버가 먼저 자동 판정하고 사용자가 결과 상세에서 `정답` 또는 `오답`으로 수정할 수 있다.
- 미응답 단답형은 사용자 수정 대상이 아니다.
- 사용자 수정이 저장되면 수정한 판정이 그 문항의 현재 채점 결과가 된다.
- 현재 채점 결과가 바뀌면 채점 점수와 복습할 문제 수를 같은 서버 상태에서 다시 계산한다.
- 사용자는 단답형의 현재 판정을 다시 수정할 수 있다.
- 서술형의 `CORRECT|PARTIAL|INCORRECT` 자기평가는 기존 별도 흐름을 유지하며 단답형 판정 수정과 합치지 않는다.

## 3. 목표 상태 모델

단답형 결과는 최소한 다음 의미를 가진다. 정확한 컬럼명과 테이블 배치는 서버 구현 시 현재 모델을 확인한 뒤 정한다.

| 의미 | 규칙 |
| --- | --- |
| 제출 답안 | 최초 제출 값을 불변 보존 |
| 현재 채점 결과 | `CORRECT` 또는 `INCORRECT`. 최초에는 서버 판정이며 사용자 수정이 저장되면 해당 값으로 변경 |
| 수정 시각 | 사용자가 판정을 수정할 때 갱신 |

사용자 수정은 해당 attempt 문항의 채점 결과만 바꾼다. 허용 답안 목록이나 같은 문제를 푼 다른 사용자의 채점 결과로 전파하지 않는다. 초기 서버 판정을 별도 감사 기록으로 남길지는 열린 질문이며, 사용자에게 보이는 현재 채점 결과와 분리한다.

## 4. 서버 처리 경계

향후 서버 구현은 다음 순서를 보장해야 한다.

1. Access Token의 현재 사용자로 attempt와 question 소유권을 확인한다.
2. 대상이 답을 작성한 `SHORT_ANSWER`인지 확인한다. 객관식·빈칸·서술형·미응답 단답형은 거절한다.
3. 요청한 `CORRECT` 또는 `INCORRECT`를 해당 문항의 현재 채점 결과로 저장한다.
4. 같은 트랜잭션에서 채점 점수와 현재 복습 대상 여부를 일관되게 계산한다.
5. 응답에는 변경된 현재 판정과 갱신된 점수·복습 요약을 함께 제공한다.

저장 응답을 확인하기 전까지 클라이언트가 점수나 복습 수를 성공 상태로 먼저 확정하지 않게 한다. 응답 유실 재시도는 같은 의미의 결과를 만들도록 멱등성을 제공해야 한다.

## 5. 프론트 선행 설계가 요구하는 상태

프론트 결과 상세는 다음 상태를 표현할 수 있어야 한다.

- `GRADED`: 현재 `정답/오답`과 `채점 수정` 표시
- `SAVING`: 기존 판정과 요약을 유지하고 수정 행동의 진행 상태 표시
- `EDITED`: 변경된 현재 판정과 `채점 다시 수정` 표시
- `SAVE_FAILED`: 기존 판정과 요약을 유지하고 재시도 제공

객관식 결과 상세와 미응답 단답형에는 수정 진입을 렌더링하지 않는다. 서버 계약이 준비되기 전에는 기기 로컬 상태만으로 운영 점수나 복습 수를 바꾸는 기능을 출시하지 않는다.

## 6. 현재 API 계약과 필요한 후속 변경

현재 API 계약은 결과에 단일 `outcome`을 제공하지만 단답형 판정 수정 엔드포인트를 정의하지 않는다. 서버 구현 전에 공유 계약에서 다음을 확정해야 한다.

- `outcome`이 가장 최근에 저장된 현재 채점 결과라는 의미
- 단답형 현재 판정을 수정하기 위한 method·path·request·response
- 소유권, 대상 유형, 미응답, 이미 완료된 복습 상태에 대한 오류 의미
- 멱등 키와 동시 수정 처리
- 사용자 수정 뒤 채점 점수와 `reviewRequired` 계산 시점
- 이미 활성 복습 세션이 만들어진 뒤 판정을 수정했을 때 세션 대상을 유지할지 갱신할지

이 항목이 API 계약에 반영되기 전에는 이 TRD의 예시 상태를 공개 계약으로 해석하지 않는다.

## 7. 기술 검증 기준

- 객관식·빈칸·서술형과 미응답 단답형의 판정 수정 요청은 저장되지 않는다.
- 단답형 수정 뒤에도 제출 답안은 변하지 않고 현재 채점 결과만 요청한 판정으로 바뀐다.
- 같은 단답형의 판정을 다시 수정하면 가장 최근에 저장한 판정이 현재 채점 결과가 된다.
- 수정 저장과 점수·복습 수 계산은 부분 반영 없이 일관된 결과를 반환한다.
- 다른 사용자의 attempt나 question에는 존재 여부를 노출하지 않고 접근할 수 없다.
- 같은 멱등 키의 같은 요청은 같은 결과를 반환하고, 응답 유실 뒤 재시도해도 수정 이력이 중복되지 않는다.
- 저장 실패 시 변경 전 판정, 점수와 복습 대상 상태가 유지된다.

## 8. 서버 구현 전 열린 질문

- 활성 복습 세션이 이미 존재할 때 원본 attempt의 단답형 판정을 수정하면 현재 세션 snapshot을 갱신할지, 다음 복습부터 반영할지 결정이 필요하다.
- 사용자 수정 이력 전체를 감사 로그로 남길지 마지막 수정 판정과 시각만 보존할지 결정이 필요하다.
