# Web Frontend Guide

이 지침은 `web/` 아래의 모든 작업에 적용된다. 루트 `AGENTS.md`의 공통 규칙과 함께 따른다.

## 기술 기준

- React, TypeScript, Vite, React Router, TanStack Query를 사용한다.
- 패키지 관리자는 `pnpm`이다.
- UI는 `@seed-design/react`와 `@seed-design/css`를 우선 사용한다.
- 작업 전 전체 코드를 읽지 말고, 관련 라우트·feature·공용 컴포넌트·API 경계를 검색해 범위를 좁힌다.

## 문서 맥락 선택

먼저 `docs/README.md`에서 현재 요청과 직접 연결된 문서만 찾는다. 작업 성격에 따라 다음 문서를 선택한다.

- 제품 동작: `docs/features/`
- 화면 구조와 상태: `docs/screens/`
- 화면 간 흐름: `docs/flows/`
- 서버 연동: `docs/contracts/api/`

문서의 상태를 확인하고 `확정 사항`, `설계 가정`, `미결정 사항`을 구분한다. 초안이나 가정을 승인된 요구사항처럼 구현하지 않는다. 기능 명세, 화면 명세와 API 계약이 충돌하면 조용히 해석하지 말고 충돌과 영향을 보고한다.

## 전문 역할 선택

사용자 요청 한 건에는 기본적으로 가장 적합한 전문 에이전트 하나만 사용한다. 사용자가 명시적으로 복수 역할을 요청하거나 작업을 안전하게 분리할 이유가 있을 때만 최대 두 개를 사용한다. 전문 에이전트가 다음 에이전트를 자동 호출하거나 설계부터 기능 연결까지 연쇄 실행하지 않는다.

- `seed_ui_designer`: UX 구조, 화면 명세, 와이어프레임 또는 비프로덕션 프로토타입을 만든다. 프로덕션 코드를 수정하지 않는다.
- `seed_publisher`: 사용자가 승인한 화면 명세를 SEED 기반 표현 UI로 구현한다. 라우팅, API, 상태와 비즈니스 로직을 연결하지 않는다.
- `frontend_engineer`: 승인된 UI를 보존하면서 라우팅, 상태, 폼, API와 사용자 동작을 연결한다. 화면을 임의 재설계하지 않는다.

각 역할은 자신의 산출물을 보고한 뒤 멈춘다. 설계 산출물을 사용자가 검토·수정한 후 별도 요청으로 구현을 시작하는 흐름이 기본이다.

## SEED Design 규칙

- SEED에 있는 컴포넌트를 raw HTML/CSS로 재구현하지 않는다.
- 컴포넌트 이름, props, 토큰과 아이콘을 추측하지 않고 SEED Docs MCP에서 확인한다.
- 하드코딩한 색상·간격보다 SEED semantic token과 recipe를 우선한다.
- 기존 공용 컴포넌트가 같은 의미와 상태를 지원하면 재사용한다.
- 적합한 SEED 구성이 없으면 커스텀 구현 전에 조합 가능성을 확인하고, 예외 이유와 접근성 영향을 보고한다.
- 시맨틱 구조, 키보드 조작, `focus-visible`, 레이블, 로딩, 비활성, 오류 상태를 보존한다.
- Figma URL이 제공된 경우에만 해당 Figma 노드를 보조 근거로 사용한다. Figma가 없다는 이유로 임의 디자인 시스템을 만들지 않는다.

## 구현 경계

- 명시적인 요청이 없으면 `web/` 밖의 프로덕션 코드를 수정하지 않는다. 합의된 문서 갱신은 요청 범위 안에서만 수행한다.
- UI 퍼블리싱 단계의 mock 데이터는 실제 데이터로 오해되지 않도록 명확히 분리한다.
- API 계약이 미확정이면 실제 계약처럼 고정하지 않는다. adapter, mock 또는 명시적인 TODO 경계를 사용하거나 계약 결정을 요청한다.
- 두 쓰기 역할이 같은 화면이나 파일을 동시에 수정하지 않게 범위를 나눈다.

## 완료 조건

코드 변경 후 `web/`에서 아래 검사를 실행하고 결과를 보고한다.

```text
pnpm typecheck
pnpm lint
pnpm build
```

화면 작업은 작은 WebView 너비, 긴 문구, 키보드 탐색과 명세에 포함된 로딩·빈 상태·오류 상태도 확인한다.
