# OpenMD 문서 운영 가이드

이 문서는 OpenMD에서 사람과 AI 에이전트가 제품·UX·기술 문서를 언제 만들고, 어떻게 나누고, 무엇을 기준으로 구현할지 판단하는 원장이다. 목적은 문서 수를 늘리는 것이 아니라 중요한 결정과 책임을 한곳에 보존하는 것이다.

## 1. 적용 범위

- 새 사용자 기능과 제품 정책 변경
- 화면 구조와 사용자 흐름 설계
- 웹·앱·서버 구현 설계
- 애플리케이션 사이의 API·메시지·데이터 계약
- 구현 중 발견한 요구사항 또는 계약 차이의 처리

단순 오탈자, 작은 스타일 수정, 기존 동작을 복원하는 명백한 버그 수정과 내부 리팩터링은 별도 제품 문서를 요구하지 않는다. 기존 계약이나 승인된 동작을 바꾼다면 변경 크기와 관계없이 해당 원장을 확인한다.

## 2. 기본 원칙

### 한 정보에는 원장 하나만 둔다

제품 우선순위, 화면 상태표, API 오류 목록을 여러 파일에 복사하지 않는다. 다른 문서에서 필요하면 원장 문서와 가능한 경우 해당 절의 앵커를 링크한다.

### 가장 작은 검토 가능한 문서로 시작한다

문서 종류는 모든 기능이 채워야 하는 체크리스트가 아니다. 현재 OpenMD는 사용자 기능당 PRD 한 개를 기본으로 하고, 실제 복잡성이 있을 때만 동반 문서를 추가한다.

### 책임을 구분하되 파일을 과도하게 나누지 않는다

PRD는 `무엇과 왜`, UX 명세는 `사용자에게 어떻게 보이고 동작하는지`, TRD는 `애플리케이션 안에서 어떻게 구현하는지`, Contract는 `애플리케이션들이 무엇을 합의하는지`를 책임진다. 한 문서로 충분한 초기 기능을 억지로 여러 파일로 나누지 않는다.

### 확정·제안·열린 질문을 구분한다

- 확정: 현재 설계·구현의 기준
- 제안: 검토 가능한 권장안
- 열린 질문: 선택에 따라 사용자 경험이나 계약이 달라지는 미결정 사항

초안 문서 안에도 확정된 부분이 있을 수 있지만, 열린 질문을 승인된 요구사항처럼 구현하지 않는다.

### 코드와 문서의 불일치는 자동으로 한쪽의 잘못이 아니다

불일치를 발견하면 어느 원장이 어떤 책임을 가지는지 확인한다. 구현자가 현재 코드나 TRD를 근거로 제품 정책·UX·공유 계약을 조용히 바꾸지 않는다.

## 3. 현재 OpenMD의 기본 방식

### 기본값

새 사용자 기능은 `docs/features/`의 집중된 PRD 한 개로 시작한다.

```text
간단한 사용자 기능
└─ PRD 1개

UX 또는 구현이 복잡한 기능
├─ PRD
└─ UX 명세, Flow 또는 TRD 중 필요한 동반 문서 1개

애플리케이션 간 공유 경계가 있는 기능
├─ PRD
├─ 필요한 UX·Flow·TRD
└─ Contract
```

`기본 1개, 복잡하면 2개`는 문서 수의 절대 상한이 아니라 시작 원칙이다. Contract나 장기간 보존할 ADR이 실제로 필요하면 추가할 수 있다.

### 두 번째 문서를 추가하는 기준

다음 중 하나가 핵심일 때만 동반 문서를 추가한다.

- 화면 구조와 사용자에게 보이는 상태를 별도로 검토·승인해야 한다.
- 여러 화면의 분기, 중단, 재개와 복구를 한 PRD에서 이해하기 어렵다.
- 구현 구조나 상태 모델이 비자명하고 선택 이유를 코드만으로 보존하기 어렵다.
- 둘 이상의 애플리케이션이 같은 입력·출력·오류 의미에 합의해야 한다.

## 4. 문서 유형과 책임

| 유형 | 기본 위치 | 책임 | 만드는 시점 |
| --- | --- | --- | --- |
| PRD | `docs/features/` | 사용자 문제, 목표, 제품 행동·정책, 범위와 관찰 가능한 수용 기준 | 새 사용자 가치 또는 제품 정책이 생길 때 |
| UX 화면 명세 | `docs/screens/` | 정보 구조, 콘텐츠·행동 위계, 진입·이탈과 사용자에게 보이는 상태 | 별도 UX 검토나 화면 상태 승인이 필요할 때 |
| Flow | `docs/flows/` | 여러 화면의 순서, 분기, 중단, 재개와 복구 | 한 화면이나 PRD로 흐름을 설명하기 어려울 때 |
| TRD | `<application>/docs/technical/` | 애플리케이션 내부 구조, 상태 모델, 컴포넌트·통합 결정과 기술 검증 | 비자명하고 지속되는 구현 판단이 있을 때 |
| Contract | `docs/contracts/` | 웹·앱·서버 사이의 입력, 출력, 오류, 권한, 멱등성과 데이터 의미 | 둘 이상의 애플리케이션이 합의해야 할 때 |
| ADR | 제품: `docs/decisions/`, 기술: 필요 시 `<application>/docs/technical/decisions/` | 검토한 선택지, 결정 이유, 영향과 대체 이력 | 여러 기능에 영향을 주거나 기능 문서보다 오래 남을 결정일 때 |

`docs/flows/`는 PRD를 보조하고, `DESIGN.md`는 전역 시각 분위기·정보 위계·레이아웃·반응형 원칙을 담당한다. 정확한 SEED 컴포넌트·props·토큰은 현재 SEED 문서와 설치 패키지가 최종 기준이다.

## 5. 문서 생성 결정 트리

1. 사용자 행동, 정책 또는 수용 기준이 바뀌는가?
   - 예: PRD를 작성하거나 기존 PRD를 갱신한다.
2. 여러 화면의 분기·중단·복구가 핵심인가?
   - 예: Flow를 추가한다.
3. 화면 구조와 사용자에게 보이는 상태를 별도로 승인해야 하는가?
   - 예: UX 화면 명세를 추가한다.
4. 구현 판단이 비자명하고 여러 작업에서 다시 참고할 가능성이 있는가?
   - 예: 해당 애플리케이션의 TRD를 추가한다.
5. 둘 이상의 애플리케이션이 같은 입출력을 사용해야 하는가?
   - 예: Contract를 별도로 작성한다.
6. 선택 이유가 현재 기능 문서의 수명보다 오래가는가?
   - 예: ADR을 검토한다.

### 새 문서를 만들지 않는 조건

- 기존 원장에 작은 절을 추가하면 충분하다.
- 기존 관례대로 구현 가능한 단순 내부 변경이다.
- 코드와 테스트가 의도를 충분히 설명하는 국소 리팩터링이다.
- 한 번 쓰고 버릴 구현 일지나 회의 메모다.
- 다른 원장의 내용을 그대로 복제하려는 목적이다.

## 6. 소스 오브 트루스와 링크 규칙

- 제품 정책과 수용 기준은 PRD가 책임진다.
- 화면 구조와 사용자에게 보이는 상태는 UX 화면 명세가 책임진다.
- 여러 화면의 순서와 분기는 Flow가 책임진다.
- 애플리케이션 간 데이터 의미는 Contract가 책임진다.
- 애플리케이션 내부 구현 방법은 TRD가 책임진다.
- TRD는 PRD·UX·Contract의 미결정 사항을 확정할 수 없다.
- `DESIGN.md`나 TRD는 현재 SEED API를 고정하거나 덮어쓸 수 없다.
- 상대 경로 링크를 사용하고 링크 문구에 대상의 책임이 드러나게 한다.
- 같은 표나 정책을 복제하지 않고 원장 절을 링크한다.
- 문서가 없다는 사실을 미결정 정책에 대한 승인으로 해석하지 않는다.

## 7. 작성·검토·구현 흐름

1. 필요한 최소 문서를 초안으로 작성한다.
2. 확정 사항, 제안과 열린 질문을 분리한다.
3. 해당 책임의 검토자가 범위와 기준을 확인한다.
4. 구현 가능한 범위를 승인한다.
5. 구현자는 승인된 원장을 기준으로 작업한다.
6. 구현 중 승인된 앱 내부 판단이 바뀌면 코드와 관련 TRD를 함께 갱신한다.
7. 제품·UX·공유 계약을 바꿔야 하면 구현을 멈추고 해당 원장 변경을 먼저 승인받는다.
8. 구현 완료 후 문서와 코드의 차이를 확인한다.

### 문서 상태

| 한글 | 영문 | 의미 |
| --- | --- | --- |
| 초안 | `draft` | 검토 전이며 바뀔 수 있음 |
| 검토 중 | `review` | 피드백을 반영하는 중 |
| 확정 | `approved` | 현재 설계·구현 기준으로 승인됨 |
| 구현 동기화 | `implemented` | 승인 상태가 아니라 구현과 맞춰졌다는 표시 |
| 폐기 | `deprecated` | 더 이상 사용하지 않으며 대체 문서를 링크함 |

## 8. 문서가 없거나 초안일 때

### 문서가 없는 경우

- 내부 리팩터링이나 기존 동작을 복원하는 버그 수정은 현재 코드·테스트·기존 계약을 기준으로 진행할 수 있다.
- 새 사용자 행동은 최소 PRD 또는 이번 요청에서 동등하게 명시된 사용자 승인이 필요하다.
- 새 공유 경계는 Contract 없이 실제 공개 계약으로 고정하지 않는다.
- TRD가 없더라도 기존 관례로 충분한 단순 구현은 진행할 수 있다.
- 비자명한 새 기술 결정을 만들 때만 최소 TRD를 작성한다.

### 문서가 초안인 경우

- 확정된 부분과 미결정 부분을 구분한다.
- 확정된 부분만 독립적으로 구현 가능하면 범위를 좁혀 진행한다.
- 열린 질문의 답에 따라 사용자 흐름, 데이터 의미나 공개 API가 달라지면 중단하고 결정을 요청한다.
- mock·adapter·TODO로 미확정 경계를 격리할 수 있으나 실제 계약처럼 표현하지 않는다.

### 문서와 코드가 충돌하는 경우

- 제품 정책은 PRD, 화면 의미는 UX 명세, 공유 입출력은 Contract의 책임을 우선 확인한다.
- TRD나 현재 코드가 상위 원장을 자동으로 이기지 않는다.
- 충돌 위치, 사용자 영향, 필요한 결정과 문서 소유자를 보고한다.

## 9. 예시 구조

### 간단한 기능

```text
docs/features/04-example.md
```

PRD 안에 목표, 제품 규칙, 필요한 화면 행동과 수용 기준을 함께 기록한다.

### UX 검토가 중요한 기능

```text
docs/features/04-example.md
docs/screens/example.md
```

PRD는 제품 행동을, 화면 명세는 정보 구조와 사용자에게 보이는 상태를 책임진다.

### 비자명한 웹 구현이 있는 기능

```text
docs/features/04-example.md
web/docs/technical/example.md
```

TRD는 상태 모델과 통합 결정을 설명하며 PRD를 재정의하지 않는다.

### 애플리케이션 간 계약이 있는 기능

```text
docs/features/04-example.md
docs/contracts/api/example.md
web/docs/technical/example.md       # 필요한 경우
server/docs/technical/example.md    # 필요한 경우
```

Contract만 공유 의미를 정의하고 각 TRD는 자신의 애플리케이션 구현을 설명한다.

## 10. 성장 단계별 발전

### 현재: 작은 팀과 초기 제품

- 기능당 PRD 한 개로 시작한다.
- 복잡할 때 동반 문서 하나를 추가한다.
- 문서 상태와 열린 질문을 사람이 직접 검토한다.
- 전체 계층이나 빈 디렉터리를 미리 만들지 않는다.

### 협업 인원이 늘어날 때

- 기능별 문서 소유자와 필수 검토자를 정한다.
- 승인자와 변경 이력을 더 명확히 기록한다.
- 반복되는 문서 구조가 실제로 생기면 템플릿을 보강한다.

### 여러 애플리케이션과 팀이 늘어날 때

- Contract 버전과 소비자 영향을 기록한다.
- 애플리케이션별 TRD와 기술 ADR을 도입한다.
- 호환성·마이그레이션 정책과 계약 검증을 강화한다.

### 제품 영역이 커질 때

- 영역별 문서 인덱스와 소유권 규칙을 만든다.
- 자동 링크 검사, 문서 상태 검사와 `CODEOWNERS` 적용을 검토한다.
- 동일한 문제가 반복될 때만 문서 사이트나 검색 도구를 도입한다.

### 성숙 단계

- 중요한 Contract를 자동 테스트나 스키마 검증과 연결한다.
- 코드·문서 동기화 검사를 CI에 추가한다.
- 실제 규모가 요구할 때만 전용 문서 포털을 운영한다.

미래 단계의 구조를 현재부터 선행 구축하지 않는다. 반복되는 비용과 협업 문제가 확인될 때 한 단계씩 도입한다.

## 11. 피해야 할 방식

- 모든 기능에 PRD·UX·Flow·TRD·Contract를 전부 생성한다.
- 화면 명세에 API 필드나 정확한 SEED props를 제품 요구사항으로 고정한다.
- TRD에서 제품 정책이나 사용자 상태를 바꾼다.
- 같은 우선순위·상태·오류 표를 여러 문서에 복사한다.
- 코드와 다르다는 이유로 승인 문서를 조용히 수정한다.
- 초안과 열린 질문을 확정 요구사항처럼 구현한다.
- 단순 회의 메모나 구현 일지를 ADR로 남긴다.
- 실제 수요가 생기기 전에 빈 문서 계층과 템플릿을 대량으로 만든다.

## 12. 체크리스트

### 문서를 만들기 전

- [ ] 사용자 행동이나 공유 계약이 실제로 바뀌는가?
- [ ] 기존 원장에 추가하는 것으로 충분하지 않은가?
- [ ] 두 번째 문서를 요구하는 실제 복잡성이 있는가?
- [ ] 이 결정은 코드와 테스트만으로 이해하기 어려운가?

### 문서를 작성할 때

- [ ] 이 문서의 책임과 비범위가 분명한가?
- [ ] 확정·제안·열린 질문이 구분됐는가?
- [ ] 다른 원장의 내용을 복제하지 않고 링크했는가?
- [ ] 수용 기준이 관찰 가능하고 구현 방식에 과도하게 종속되지 않았는가?

### 구현을 시작할 때

- [ ] 구현할 범위가 승인됐는가?
- [ ] 필요한 최소 PRD·화면·계약만 확인했는가?
- [ ] 관련 TRD가 없더라도 기존 관례로 충분한 단순 구현인가?
- [ ] 열린 질문을 구현 가정으로 승격하지 않았는가?
- [ ] 변경해야 할 원장과 구현 책임자가 분명한가?

### 구현을 마칠 때

- [ ] 코드가 승인된 제품·UX·계약을 보존하는가?
- [ ] 비자명한 구현 결정만 필요한 TRD에 반영했는가?
- [ ] 직접 영향받은 Contract와 문서 링크가 최신인가?
- [ ] 남은 mock·TODO·미결정 경계를 보고했는가?
