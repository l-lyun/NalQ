# [PRD] 퀴즈 생성 결과 OS 푸시 알림

## 문서 책임

이 문서는 앱이 background이거나 종료된 동안에도 퀴즈 생성 결과를 운영체제 푸시로 알리는 후속 제품 확장의 범위와 검토할 정책을 정의한다. 기기 등록, 발송 상태와 외부 제공자 연동의 공유 의미는 이 PRD 승인 뒤 별도 Contract에서 정한다.

선행 PRD에서 OS 푸시가 비범위인 것은 현재 알림함 버전의 범위를 뜻한다. 이 문서는 기존 알림함을 대체하지 않고 같은 생성 결과 사건을 앱 밖으로 전달하는 다음 버전을 제안한다.

## 결정 상태

- **확정**: 퀴즈 생성 결과를 OS 푸시로 알리는 기능의 제품 설계를 시작한다.
- **확정**: iOS 우선 적용, 가까운 시일 내 Android 후속 지원을 고려해 두 플랫폼을 설계한다.
- **확정**: 생성 성공·실패 모두 발송한다. 푸시 선택 시 성공은 내 퀴즈 목록의 해당 퀴즈로, 실패는 해당 자료의 생성 조건 화면으로 바로 이동한다.
- **확정**: MVP는 첫 로그인 직후 별도 사전 안내 없이 OS 알림 권한을 요청한다. 허용하면 성공·실패 푸시를 자동 활성화하고 별도 서비스 수신 설정은 두지 않는다.
- **확정**: 푸시 권한 요청과 기기 등록은 앱에서 로그인한 경우에만 실행하며 일반 웹 브라우저에서는 실행하지 않는다. MVP는 이 기능 진입 구분을 제공하고 위조 요청까지 구분하는 정식 앱 증명은 후속 범위로 둔다. 서버의 사용자 인증과 기기 소유권 검증은 유지한다.
- **확정**: 앱 푸시 수신 기기가 등록된 사용자는 퀴즈 생성 요청이 웹 또는 앱 중 어디에서 시작됐는지와 관계없이 성공·실패 결과를 앱으로 받는다. 현재 권한이 허용되고 계정에 연결된 기기를 대상으로 한다.
- **제안**: 위 확정 사항 외 정책과 수용 기준은 사용자 검토 전이다.
- **열린 질문**: 선택에 따라 사용자 흐름 또는 공유 계약이 달라지는 항목은 문서 마지막에 둔다.

## 사용자 문제

현재 알림함과 Snackbar는 웹 또는 앱이 실행 중이거나 사용자가 다시 돌아왔을 때 결과를 확인하게 한다. 앱이 background이거나 종료돼 있으면 퀴즈가 완성되거나 실패해도 바로 알기 어렵고, 사용자가 직접 앱을 다시 열어야 한다.

## 목표 — 제안

- 사용자는 앱 밖에서도 자신이 요청한 퀴즈의 생성 성공·실패를 알 수 있다.
- 푸시를 선택한 사용자는 해당 퀴즈를 확인하거나 해당 자료의 생성 조건을 조정할 수 있다.
- 푸시 전달 여부와 기존 알림함의 읽음 상태를 구분해 여러 기기에서도 결과 기록을 신뢰할 수 있다.
- 푸시 권한을 허용하지 않아도 기존 알림함과 foreground Snackbar로 결과를 확인할 수 있다.

## 범위 — 개별 결정 상태

- **확정**: iOS 앱의 퀴즈 생성 성공·실패 OS 푸시를 우선 제공
- **확정**: Android 앱도 가까운 시일 내 후속 지원하며 초기 설계부터 두 플랫폼 고려
- **확정**: 첫 로그인 직후 OS 알림 권한 요청 및 허용 시 성공·실패 푸시 자동 활성화
- **확정**: 같은 계정으로 로그인하고 알림을 허용한 모든 등록 앱 기기에 생성 결과 전달
- **확정**: 성공 푸시 선택 시 내 퀴즈 목록의 해당 퀴즈로, 실패 푸시 선택 시 해당 자료의 생성 조건 화면으로 직접 이동
- 권한 거절, 로그아웃·계정 전환, 인증 만료, 대상 삭제와 중복·지연 전달의 안전한 처리

## 비범위 — 제안

- 모바일·데스크톱 웹 브라우저 푸시
- 생성 결과 외 마케팅, 학습 리마인드와 운영 공지
- 예약 발송, 방해 금지 시간과 종류별 상세 수신 설정
- 푸시만으로 퀴즈 화면을 자동 실행하거나 풀이를 시작하는 행동
- 특정 외부 푸시 제공자, API, 저장 구조와 재시도 횟수의 제품 계약 고정
- 운영체제 정책과 네트워크 상태를 넘어서는 즉시 또는 절대 도달 보장

## 핵심 정책 — 제안

### 기존 알림함과의 관계

- 푸시는 기존 서버 알림 한 건을 앱 밖으로 전달하는 추가 경로다. 같은 QuizSet에 별도의 사용자 알림 사건을 만들지 않는다.
- 성공과 실패 종류, 대상, 생성 시각은 기존 알림 원장의 의미를 재사용한다.
- 푸시가 발송·수신·표시된 사실만으로 서버 알림을 읽음 처리하지 않는다.
- **확정**: 사용자가 푸시를 선택해 해당 결과의 목적지 화면에 진입하면 알림함에서도 그 알림을 읽음 처리한다. 단순 발송·수신·표시나 OS 알림 삭제는 읽음 처리가 아니다. 로그인 화면으로 안내한 시점에는 읽음 처리하지 않는다. 대상이 삭제된 경우에는 아래 대상 없음 복구 규칙에 따라 읽음 처리한다.
- **확정**: 읽음 처리 요청만 실패하면 완료한 화면 이동을 유지하고 오류 팝업 없이 재시도한다. 미반영 읽음 처리는 다음 앱 접속 때에도 같은 계정에서 동기화한다. 다른 계정으로 미반영 처리를 보내지 않으며, 재시도 간격·횟수와 만료 알림 처리 방식은 후속 기술 설계에서 정한다.
- 푸시가 전달되지 않아도 기존 알림함에는 생성 결과가 남고 다음 앱 진입에서 확인할 수 있다.
- **확정**: 푸시 신규 발송과 재시도는 생성 성공·실패 결과가 확정된 시각부터 1시간까지만 수행한다. 재시도나 서버 재시작으로 이 기한을 연장하지 않는다. 이후에는 기존 알림함에서 결과를 확인한다. 이미 표시된 OS 알림을 삭제하거나 기존 알림함의 90일 보존·읽음 동기화 기간을 줄이는 정책은 아니다.

### 알림 대상과 문구

- **확정**: 성공과 `SOURCE_INSUFFICIENT`, `GENERATION_FAILED` 실패를 모두 발송 대상으로 한다.
- **확정**: 성공·실패 푸시 모두 퀴즈 제목을 포함한다. 기존 알림 원장에 저장된 생성 당시 퀴즈 제목을 사용한다. 잠금화면 미리보기는 사용자의 OS 설정을 따른다.
- **문구 제안**: 푸시 제목은 퀴즈 제목, 본문은 성공 시 `퀴즈가 완성됐어요.`, 실패 시 `퀴즈를 만들지 못했어요. 앱에서 확인해 주세요.`로 구성한다. 상세 확인과 복구는 인증 뒤 결과별 목적지에서 제공한다.
- **제안**: 학습자료 본문, 문제·정답과 상세 실패 원인은 푸시에 포함하지 않는다.
- 같은 결과가 제공자의 재시도나 여러 경로로 중복 도착해도 한 기기에서 같은 알림을 반복 표시하지 않는 것을 목표로 한다.

### 권한 요청 — 확정

- 앱에서 첫 로그인 직후 별도의 앱 내 사전 안내나 허용 버튼 없이 OS 알림 권한을 요청한다. 일반 웹 브라우저 로그인에는 이 흐름을 실행하지 않는다.
- OS 알림 권한을 허용하면 생성 성공·실패 푸시가 자동 활성화된다. 추가 동의나 NalQ 수신 토글은 MVP에 두지 않는다.
- 이미 권한을 결정한 기기에서는 로그인할 때마다 반복 요청하지 않고 현재 OS 권한 상태를 따른다.
- 권한 허용은 수신 기능 활성화를 뜻하며 즉시 또는 절대 도달을 보장하는 것은 아니다.
- **제안**: 거절해도 생성과 기존 알림함 사용에는 영향이 없고, 필요한 맥락에서 OS 설정 변경 방법을 안내한다.

### 수신 기기와 계정 경계

- **확정**: 앱 접속과 로그인 사용자 연결을 확인한 기기만 푸시 등록 대상으로 삼는다. 웹 로그인만으로 푸시 기기를 등록하거나 수신 대상으로 간주하지 않는다.
- **확정**: 앱 수신 기기가 등록돼 있으면 웹에서 생성한 퀴즈도 앱 푸시 발송 대상이다. 생성 요청의 접속 채널로 발송을 제한하지 않는다.
- **확정**: 같은 사용자로 로그인되어 있고 푸시 권한이 유효한 모든 등록 앱 기기에 발송한다. 새 기기에 로그인해도 앞서 등록한 기기를 수신 대상에서 대체하지 않는다.
- 로그아웃한 기기에는 이후 결과의 신규 발송을 중단한다. 다른 계정으로 전환하면 이전 계정의 상세 내용을 보여주지 않는다.
- 로그아웃·탈퇴 전에 이미 외부 제공자에 전달한 푸시는 퀴즈 제목과 함께 뒤늦게 표시될 수 있다. 표시 취소를 보장하지 않으며, 선택 시 현재 계정의 권한을 다시 확인한다.
- 회원 탈퇴가 확정되면 해당 계정의 모든 기기는 이후 푸시 대상에서 제외돼야 한다.
- **확정**: 인증이 만료된 상태에서 푸시를 선택하면 로그인 화면으로 안내하고 선택한 알림과 원래 목적지를 보존한다. 같은 계정으로 로그인하면 성공은 내 퀴즈 목록의 해당 퀴즈로, 실패는 해당 자료의 생성 조건 화면으로 이어진다. 목적지 진입 시 해당 알림을 읽음 처리한다.
- 다른 계정으로 로그인하면 이전 계정의 목적지로 이동하거나 해당 알림을 읽음 처리하지 않는다. 이전 계정의 상세 정보를 노출하지 않는 기존 계정 경계를 유지한다.

### 앱 상태와 선택 행동

- **확정**: 해당 기기에서 앱을 사용 중(foreground)이면 OS 푸시 알림을 표시하지 않는다. 배너·알림음·진동 등 OS 알림으로 추가로 주의를 끌지 않고 기존 앱 내 Snackbar와 알림함 규칙을 유지한다. 생성 화면 등 기존 Snackbar 비노출 조건도 그대로 따른다.
- **확정**: 사용 중 여부는 기기별로 판단한다. 한 기기에서 앱을 사용 중이어도 다른 기기의 background·종료 상태 푸시 표시를 막지 않는다. 발송 여부와 foreground 표시 억제의 구현 방식은 후속 기술 설계에서 정한다.
- **확정**: 푸시를 선택하면 성공은 내 퀴즈 목록의 해당 퀴즈로, 실패는 해당 자료의 생성 조건 화면으로 직접 이동한다. 퀴즈 풀이나 재생성을 자동 시작하지 않는다.
- 푸시가 오래 지연됐거나 앱 진입 전에 대상이 삭제된 경우에도 결과 상세를 추정하거나 다른 사용자의 화면을 열지 않는다.
- 알림함에서 대상 항목을 선택한 뒤 대상이 없으면 기존 `대상을 찾을 수 없어요.` 안내와 읽음 규칙을 따른다.
- **확정**: 푸시를 선택했으나 대상 퀴즈 또는 원본 자료가 삭제돼 목적지에 진입할 수 없으면 `대상을 찾을 수 없어요.`라고 안내한 뒤 알림함으로 이동하고 해당 알림을 읽음 처리한다. 현재 계정 소유의 알림에만 적용하며 일시적인 조회 실패를 삭제로 단정하지 않는다.
- 운영체제 알림을 지우는 행동은 NalQ 알림함의 읽음 또는 삭제로 해석하지 않는다.

| --- | --- | --- |
| 권한 허용 | background·종료 상태에서 결과 푸시를 받을 수 있음 | 푸시 선택 시 인증 확인 뒤 결과별 목적지로 이동 |

| 인증 만료 상태에서 선택 | 로그인 화면으로 안내하며 알림은 아직 읽음 처리하지 않음 | 같은 계정으로 로그인하면 원래 목적지로 이동하고 진입 시 읽음 처리(확정) |
| 대상 삭제 | `대상을 찾을 수 없어요.` 안내 | 알림함으로 이동하고 해당 알림 읽음 처리(확정) |
| 회원 탈퇴 | 이후 계정 푸시 신규 발송 중단 | 모든 활성 기기를 수신 대상에서 제외, 이미 발송한 푸시로 상세 접근 불가 |

## 수용 기준 — 제안

- [ ] **확정**: iOS 우선으로 새 성공·실패 결과 푸시를 제공하며 Android 후속 지원을 고려한다.
- [ ] **확정**: 앱의 권한 미결정 기기는 첫 로그인 직후 별도 사전 안내 없이 OS 알림 권한을 요청한다. 일반 웹 로그인에서는 권한 요청이나 푸시 기기 등록이 실행되지 않는다.
- [ ] **확정**: OS 권한 허용 시 추가 동의나 서비스 수신 토글 없이 성공·실패 푸시가 활성화된다.
- [ ] **확정**: 같은 계정으로 두 기기를 등록하고 각각 알림을 허용하면 두 기기 모두 생성 결과 발송 대상이 된다. 나중에 등록한 기기가 기존 기기의 등록을 덮어쓰지 않는다.
- [ ] **확정**: 앱 수신 기기가 등록된 계정은 웹에서 퀴즈를 생성해도 앱으로 성공·실패 푸시를 받는 대상이 된다. 웹만 이용하고 앱 기기를 등록하지 않은 계정은 푸시 발송 대상이 아니다.
- [ ] 권한 거절 또는 푸시 전달 실패가 퀴즈 생성, 기존 Snackbar와 서버 알림함을 막지 않는다.
- [ ] **확정**: 앱 사용 중인 기기는 OS 푸시 표시·알림음·진동 없이 기존 결과 UI만 사용한다. 다른 기기가 background·종료 상태라면 그 기기는 계속 푸시 표시 대상이다.
- [ ] **확정**: 성공·실패 푸시 모두 알림 원장에 저장된 퀴즈 제목을 포함하며, 실제 잠금화면 미리보기는 OS 설정을 따른다.
- [ ] 학습자료 본문·문제·정답과 상세 실패 원인은 푸시에 포함하지 않는다.
- [ ] **확정**: 성공 푸시 선택은 내 퀴즈 목록의 해당 퀴즈로, 실패 푸시 선택은 해당 자료의 생성 조건 화면으로 직접 연결된다.
- [ ] **확정**: 푸시를 선택해 목적지 화면에 진입하면 해당 알림이 서버 알림함에서도 읽음 처리된다. 다른 알림의 읽음 상태는 바꾸지 않으며 단순 수신·표시는 읽음 처리하지 않는다.
- [ ] **확정**: 인증 만료 상태에서 푸시를 선택하면 로그인으로 안내하고, 같은 계정으로 로그인한 뒤 원래 결과별 목적지로 이어진다. 로그인 안내만으로 읽음 처리하지 않는다.
- [ ] **확정**: 대상 퀴즈 또는 원본 자료가 삭제된 푸시를 선택하면 `대상을 찾을 수 없어요.` 안내 후 알림함으로 이동하고 해당 알림만 읽음 처리한다.
- [ ] **확정**: 읽음 요청이 실패해도 화면 이동이 취소되거나 오류 팝업이 나타나지 않는다. 일시적 실패가 해소되면 재시도로 서버 읽음 상태를 반영하며, 앱 종료 후 다음 접속에서도 같은 계정의 미반영 처리를 동기화한다.
- [ ] 로그아웃·계정 전환·회원 탈퇴가 반영되면 이전 계정의 신규 발송이 중단되고, 이미 발송된 푸시를 선택해도 이전 계정의 개인 상세에 접근할 수 없다.
- [ ] 지연·중복 전달과 대상 삭제 상황에서도 다른 사용자의 정보나 잘못된 목적지를 열지 않는다.
- [ ] OS 푸시가 도착하지 않아도 생성 결과는 기존 서버 알림함에서 확인할 수 있다.
- [ ] **확정**: 결과 확정 후 1시간이 지나면 미발송·재시도 작업의 새 전송을 중단하고, 알림함의 결과는 기존 보존 규칙에 따라 유지한다.

## 계측 제안

- 첫 로그인 뒤 운영체제 권한 요청과 권한 결과
- 결과 종류별 발송 시도·표시 가능 결과·푸시 선택과 결과별 목적지 진입

- 퀴즈 제목, 학습자료 내용, 문제·정답과 외부 제공자의 원시 payload는 분석 사건에 포함하지 않는다.

## 소급·복구·보존 정책

- **확정**: 소급 발송하지 않는다. 기능 활성화 전 결과와 기기 등록 전 결과는 발송 대상에 추가하지 않는다. 재설치·토큰 복구도 과거 알림 재발송을 유발하지 않는다.
- **확정(2026-09-06 정책 승인)**: 앱 실행·로그인·foreground 복귀 때 권한과 현재 토큰을 재확인한다. 설치 자격이 남으면 기존 연결을 갱신하고, 자격이 유실돼도 같은 계정·같은 토큰이면 새 설치로 자동 이관한다. 다른 정상 기기의 연결은 유지한다.
- **확정(2026-09-06 정책 승인)**: 설치 자격이 없고 토큰이 다른 계정 소유이면 자동 이관하지 않는다. 이전 계정으로 로그인해 연결을 복구한 뒤 로그아웃/해제하고 새 계정에서 등록한다. 이전 계정 접근도 불가능하면 푸시 등록만 보류하고 계정 복구를 안내한다. 퀴즈 이용은 막지 않는다. 별도의 푸시 소유 증명 challenge는 MVP 기본 흐름에 추가하지 않는다.
- **확정**: 알림 자체가 없거나 만료됐으면 `알림을 찾을 수 없어요.` 안내 후 현재 계정 알림함으로 이동하며 읽음 요청을 만들지 않는다. 읽음 대기 기록은 로그아웃 시 정지·격리하고 같은 계정 복귀 시 재개하며 알림 생성 후 90일 또는 탈퇴 시 정리한다.
- **확정**: 멱등 응답 기록은 최초 처리 후 7일, 비활성 설치 기록은 마지막 활성 연결이 종료된 때부터 30일 뒤 정리한다. 발송용 토큰은 비활성화 즉시 제거한다. 활성 기기를 기간만으로 해제하는 정책은 아니다. 오래된 변경 요청의 재생 방지는 공유 계약에서 구체화한다.
- **결정(사용자 위임)**: 서버 발송·receipt 진단 기록은 delivery 생성 시각부터 30일 보관한다. 일주일보다 긴 문의·간헐 장애 확인에 사용하며, 알림 ID·기기 참조·상태·시각·시도 횟수·정규화 오류 등 최소 메타데이터만 보관한다. 퀴즈 제목·본문·원시 토큰·전체 제공자 응답은 복제하지 않는다. 이는 법정 보존 기간이 아닌 운영 정책이다. 기존 알림함의 90일과 활성 기기의 토큰 수명은 별개다.

## 후속 설계 사항

대화에서 논의한 제품 선택은 합의됐다. 문서의 나머지 `제안` 항목은 개별 승인 또는 후속 검토 대상으로 남으며, 문서 전체가 구현 승인된 것은 아니다.

- 앱 접속 검증, 기기 등록·계정 연결과 웹·네이티브 메시지의 공유 계약
- 확정된 발송 제공자에 대한 기기별 전달·재시도와 중복 처리
- 읽음 재시도의 유지 범위·종료 조건과 만료된 알림 처리

발송 제공자는 2026-09-06 사용자 합의로 Expo Push Service를 선택했다. 구체적인 연결 방식은 기술 설계안이 소유한다. 선행 Contract의 FCM 언급은 기존 확장 경계 예시이며, Expo 전달 구조에 맞는 공유 계약은 후속 작성한다.
